# Current alpha scope and handoff

Status: owner is preparing a quick alpha from current capabilities, 2026-11-09.
The alpha is intended to be publicly hosted as a discoverable Polylith app.
The owner will handle hosting and integration into the parent installation.
No external host/repository changes or deployment were performed here.

## Scope

Use the current Flat app: Flat/Globe modes, shared location/date/time,
independent cameras, optional second view, camera sync and existing controls.
The [main README](../../../../README.md) explains current model assumptions.
Refraction and the [solar calibration alternatives](../../flat/overhead-sun-calibration.md)
remain deferred. The scene-object investigation has not started. This alpha
intent does not close or remove the separate [MVP goals](../mvp/requirements.md).

## Repository readiness

The [production catalog](../runtime-integration/flat32-production-exclusion.md)
advertises only Flat and preserves Flat32 through explicit development commands.
Standalone hosting restricts static serving to Flat's output. Parent deployments
must remove any stale Flat32 output/registration they previously hosted.
The host uses `NODE_ENV=prod`; the runbook follows that name. The base production
catalog works with either `prod` or `production`, and the Flat32 development
launcher rejects both values.

The generic `npm run build` no longer invokes the Flat32-only worker builder.
Flat's own Polylith feature generates its worker at the selected deployment
destination. The repository-wide build succeeds with `NODE_ENV=production`;
the generated `dist/flat/shared-cache-worker.js` is present. Explicit Flat32
builds retain their own worker step. The preceding local verification records
31 passing server tests and actual production-host 200/404 route checks.
These are local readiness checks, not a new deployed-host or full scientific
qualification result.

separate building/copying. These environment variables remain optional location

Sizes were measured on 2026-11-09. The newly repository-tracked stellar/vision
data totals 3,411,648 bytes (about 3.41 MB). The city database is already
Git-tracked (10,359,165 bytes); Polylith copies it during the app build. Browser
JavaScript, CSS and the shared-cache worker are generated by that build, and npm
dependencies are installed from the lockfile. They are not additional manual
data-provisioning packages. No research/archive dataset is required by the
current running app beyond the operational packages identified here.

The [stellar data instructions](../../../../server/flat/data/README.md) own
package identities and provisioning. The cache service selects the published
package identity in `server/common/distant-sun-package.js`; temporary `staging-*`
directories are not the deployment package. Flat's local-Sun cache is generated
at browser startup.

Measured on 2026-11-09, the published spherical package contains **734,130,872
bytes (700.12 MiB)** across 209 files, including 95 Zstandard-compressed blocks.
The largest block is 9,494,780 bytes (9.05 MiB). An additional local `staging-*`
directory occupies the same total size and is not selected for serving; deploy
only the published package. Clients request selected blocks rather than one
monolithic package download. Flat's generated local-Sun cache requires no
prebuilt host cache files.

## Selected cache provisioning workflow

The owner selected **local GPU generation after pulling the intended Git
revision, then copying the completed package to Ubuntu**. The web host serves
the cache and does not need Chrome or GPU access. The
[deployment runbook](../../deploy/README.md) owns exact commands, the compact
tracked metadata seed, the transferable build subset, Flat's destination,
generated-identity activation, verification and rollback. Host-side generation
is not the selected deployment workflow.

The runbook also owns portable input-fingerprint checks. Local builds reuse
unchanged available output before starting Chrome, and the Ubuntu installation
can compare its receipt before another copy. Preserve the transferred and
installed receipts with their cache data across releases. Older unrecorded
packages remain usable but cannot claim an unchanged-input match.

Repository tracking does not change the stellar/vision manifests' recorded
source/redistribution status. [T13](../mvp/requirements.md#t13) continues to own
the remaining clearance work; no data-clearance finding is claimed here.
