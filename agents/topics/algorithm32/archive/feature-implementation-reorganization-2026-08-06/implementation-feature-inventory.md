## Classification And Closure

The inventory distinguishes exported syntax from the current caller surface.
The six Flat32 modules listed in the final table are the only runtime files
outside `src/algorithm32` whose imports resolve into the production tree. They
form 25 import edges and consume 20 unique bindings. An `externally consumed`
row records that evidence; it does not pre-approve the binding's final public
path or feature owner.

The currently caller-instantiated or caller-selected implementation evidence
is `Algorithm32`, `CanonicalAtmosphere`, `BrunetonColorDisplayModel`,
`FlatEarthGeometry`, `SphericalEarthGeometry`, `DistantSunLightSource`,
`LocalSunLightSource`, `ThreeCacheBackend`, `FlatSynchronizer`, and
`DEFAULT_NATIVE_PRODUCTION_PROFILE`. The remaining externally consumed
bindings are adapter, math, constant, count, or owner-token support used by
those callers. Step 2 assigns every item in both groups its final feature or
internal owner; it does not need to rediscover the current surface.

Every exported class or value without a resolving external consumer is
classified here as module-exported internal/support. That includes values
re-exported by the seven family barrels: there is no current root package
export or canonical Algorithm32 public barrel. Step 2 may deliberately promote
one of those values into the new public implementation surface, but module
syntax alone does not make it current public API. This closes the classification
without prejudging the target-owner decisions that belong to Step 2.

The class audit found 67 exported-class modules: 54 named exported class
declarations and 13 default-exported class declarations. The plan's former
count of 54 omitted the default-export set. The ambient declaration audit found
45 interfaces in 24 files. Each appears once in the tables below.

  consumers, and this reorganization does not rewrite historical records.
