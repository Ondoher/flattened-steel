## Objective

Deliver one production Algorithm32 implementation that:

- keeps atmospheric and boundary composition spectral until one final RGB
  conversion;
- defaults to cumulative scattering through order 4;
- builds its scattering cache on the GPU through the atmospheric light source;
- samples one source-owned cumulative local scattering-density field per
  participating atmospheric light source during view-ray integration, without
  the legacy incident-direction loop;
- supports the selected spherical/distant configuration first;
- requires the selected flat/local configuration before the complete
  Algorithm32 implementation is accepted; and
- retains clean geometry, source, atmosphere, ground, cache, and display
  boundaries across both supported paths without requiring unused geometry/
  source cross-pairings.

Plain `Algorithm32` means `maximumScatteringOrder = 4`. The supported
first-release requested maxima are 1, 2, and 4; changing among them causes a
complete cache rebuild. Order 1 contains no multiple scattering. Order 2
exercises pure second-order scattering and publishes `J1 + J2`. The default
order-4 build publishes `J1 + J2 + J3 + J4`; it necessarily constructs pure
`J3` internally, but order 3 is not a standalone requested configuration.

The canonical
[supported geometry/source pairings](architecture-boundaries.md#supported-geometry-and-source-pairings)
are spherical geometry with the distant Sun and flat geometry with the finite-
distance local Sun. Geometry and source owners remain intentionally
independent, but spherical/local and flat/distant are not production, parity,
application, or release requirements for this project.

## Sequencing Policy

Development proceeds in two passes.

1. **Visible integration:** land the capability path in the delivery order
   above, using focused smoke checks and the narrow diagnostics needed to keep
   development moving.
2. **Hardening and release acceptance:** complete source/fixture citations,
   import provenance, standalone parity, and the full unit and integration
   test surface after the visible path is integrated.

Broad reference completion, release-level coverage, and full integrated
testing are therefore follow-on work rather than prerequisites for beginning a
visible capability stage. The focused independent affected-output comparison
required by the
[conformance rules](architecture-boundaries.md#required-independent-output-evidence)
is not follow-on hardening: it must pass before a promoted algorithm is called
complete, accepted, or an oracle. A capability may advance as
implemented-but-validation-pending only when the plan states that status
explicitly; it may not supply the accepted numerical oracle for its GPU stage.

Each visible capability phase follows a CPU-to-GPU completion loop:

1. implement the CPU contract and deterministic CPU behavior;
2. integrate the corresponding GPU construction/runtime path against that
   contract; and
3. resolve the focused CPU/GPU parity and lifecycle seams for that capability.

A phase is not complete when only its CPU version exists. Move to the next
completed capability only after its GPU counterpart is integrated; complete
release-level test coverage remains follow-on hardening.

For the cache phase specifically, the accepted production construction path
will move to GPU cache building. The CPU recurrence remains a deterministic
oracle and parity surface, not a parallel production builder after that move.

Contract changes are direct replacements. Update the owning production type,
all producers and consumers, and their tests as one change, then delete the
retired shape. Do not retain aliases, fallback readers, versioned shadow
contracts, compatibility translation bridges, or old/new switches. This rule
applies during every stage; removal of a superseded algorithm strategy is not
a reason to defer contract cleanup until a later stage.

The recurrence remains:

```text
J1 = primaryScatteringDensity(lightSource, atmosphere)
JthroughN = J1

if N >= 2:
  L1 = primaryTransportedRadiance(lightSource, atmosphere)

for k = 2 through N:
  Jk = scatter(L(k - 1))
  JthroughN += Jk
  if k < N:
    Lk = transport(Jk)
```

`J1` and `L1` are separate source-specific primary fields in the retained
production implementation selected during the historical Star work. Generic
stored-field transport begins with `J2 -> L2`; it
does not replace the direct primary `L1` seed. Only a pure preceding order
feeds the next order. The cumulative field never feeds the recurrence.

## Ownership Boundaries

- **Atmosphere** owns medium profiles, spectral coefficients, phase functions,
  optical depth, and transmittance.
- **Geometry** owns physical nodes, atmosphere/ground ray bounds,
  node-to-physical reconstruction, physical-position stencils, and
  source-relative framing. It never reads cache values.
- **Atmospheric light source** owns its concrete cache type, source-specific
  `J1`/`L1`, physical domains and mapping, storage/layout implementation,
  direct source-owned plan identity and reuse-key policy, and the controller
  factory. Each source-created per-runtime controller owns build scheduling,
  invalidation, staging, publication, failure isolation, and disposal for one
  consumer. Distant Sun and local Sun caches remain distinct concrete
  implementations.
- **Generic order builder** owns source-independent `L(k-1) -> Jk` and optional
  `Jk -> Lk`. It has no camera, object, RGB, or display dependency.
- **Ground boundary** owns reflection evaluation, not geometry or profile data.
- **Shared cache contract** defines completed-cache behavior and lifetime. The
  CPU capability adds synchronous sampling and direct sample provenance for
  the oracle; the GPU capability adds opaque runtime bindings and a final-view
  shader contribution without a synchronous readback sampler. No shared
  interface is a universal concrete cache class.
- **Concrete source cache** owns direct field identity, logical layout,
  packing, shader-addressing definition, reconstruction mapping, and physical
  provenance where sampled. The renderer backend owns physical allocation,
  and the executor owns pass/layer submission. No cache infers physical
  coordinates from texture dimensions.
- **Algorithm32** owns view traversal, view transmittance, cache queries, path
  quadrature, and spectral accumulation.
- **Composition/color adapter** owns scene endpoints, accepted
  extra-atmosphere contributions, and the one final RGB boundary.

The core stays renderer-neutral. A renderer adapter supplies GPU resources,
object hit distance, and presentation. Three.js may own object materials and
shadows in the Flat app, but is not atmospheric-physics infrastructure.

## Spectral Quantity Policy

Bare arrays are not a general production boundary. Spectral packets carry the
physical quantity, unit as data, wavelength basis, point/bin semantics,
channel values, and required normalization/provenance identity.

Supported alternate units normalize before arithmetic. Addition and
comparison require compatible normalized units; multiplication and division
derive units; spectral integration applies wavelength-bin units exactly once.
The public quantity API validates and normalizes accepted packets before they
enter construction. Shaders consume that fixed canonical scalar
representation without revalidating it at the CPU/GPU seam. Spectral packets
and fields retain their direct quantity, unit, basis, precision, and
provenance contracts only where the calculation or compatibility checks
consume them. The complete retirement and direct assembly-declaration
boundary is owned by
[reconciliation Step 2.9](../archive/reconciliation-2026-08-04/algorithm32/reconciliation-plan.md#29-retire-descriptors-and-justify-assembly-declarations).

## Extension Boundaries

- Static objects shorten view rays and do not enter cache construction.
- Renderer materials and shadows remain renderer concerns. Atmospheric object
  shadows and volumetric shafts are deferred.
- Extra-atmosphere point and extended sources compose after atmosphere exit
  and neither seed nor invalidate this cache.
- The required finite-distance local Sun reuses the generic later-order
  builder, consumes geometry-owned source-relative mapping, and owns a new
  primary field and full-rebuild lifecycle.
- Required flat geometry implements the geometry contract; it does not add
  flat-only coordinates to the generic cache.

### 3. Implement the distant-Sun CPU recurrence and cache

#### 3.1 Establish shared field operations and distant-cache CPU storage

Status: complete as a structural CPU stage. This does not claim physical N=1,
a resident cache, GPU construction, or completion of the cache capability.

- Implement binary64 CPU storage for the concrete distant-Sun cache's pure
  scattering-density fields `Jk`, pure transported-radiance fields `Lk`, and
  cumulative scattering density `JthroughN`.
- Define the distant-Sun storage packing once in source-owned code. The
  concrete cache implements executable CPU offset calculation, packing, and
  accessors from that definition; the GPU path later implements its allocation
  and shader addressing from the same definition.
- Emit a readonly layout descriptor that declares the resulting axis order,
  shape, scalar format, precision, and byte count for identity, reporting, and
  diagnostics. The descriptor is data: it does not validate another value,
  calculate offsets, allocate resources, pack values, or generate shader
  addressing.
- Storage dimensions never imply physical coordinates or make indices
  interchangeable across domains. The distant-Sun layout does not prescribe
  the later local-Sun cache layout.
- Carry quantity, units, basis, position domain, direction domain, precision,
  layout, and order through ambient readonly contracts. Builder inputs are
  trusted production values rather than a new validation boundary.
- Implement one source-independent `buildNextScatteringOrder` contract and a
  separate cumulative accumulator. The builder accepts only a pure preceding
  radiance order; the accumulator accepts pure `Jk` fields; cumulative fields
  can never enter recurrence.
- Use the canonical black-ground identity for the initial cache capability.
  Keep the boundary identity seam in fingerprints without implementing
  reflective ground behavior in this phase.

The landed implementation provides source-owned executable Fibonacci-34 and

binary64 fields, distant-Sun factories for pure `Lk`, pure `Jk`, and cumulative
`JthroughN`, a synchronous pure-radiance-to-pure-scattering builder boundary,
and a separate contiguous pure-`J` accumulator. Both operations restore a

synchronous kernels may intentionally leave zero-initialized scalars

- Initialize `Jthrough1` from pure `J1`, then stop. An N=1 request constructs

- Have the source-owned `buildCpuScatteringCache` entry dispatch an explicit
  N1 request through `buildDistantSunCpuCache` and return the N1

- Check that `Jthrough1 = J1`, zero source or zero scattering yields zero, no

paths, the canonical axisymmetric atmosphere, and a native non-comparison
