# Stage 12 Extraterrestrial Experiment

This directory is the complete implementation and qualification-control root
for the active stellar screen-palette experiment. Keep new implementation,
adapted production copies, contract types, fixtures, proof runners, harness
code, manifests, package locks, and containment controls below this directory.
`../../src/algorithm32/` and `../../src/flat32/` are read-only comparison
surfaces until an explicit promotion decision.

All generated experiment execution and qualification output must resolve
below:

```text
../../tmp/extraterrestrial/
```

This includes runs, builds, browser bundles, profiles, caches, reports, GPU
readbacks, captures, diagnostics, renders, logs, temporary files, and
generated intermediates. Never write such output below
`scripts/extraterrestrial/` or commit it. A later contained experiment may
reuse generated artifacts as data, cache content, configuration, fixtures,
comparison evidence, or oracle input. The sole reuse restriction is preserving
the prior evidence: never modify, overwrite, delete, or reopen the source run
or any source artifact; write copies and derivatives into a new run. Record the
source and compatibility identities needed to substantiate a claim, but treat
that as evidence quality rather than permission to reuse. Every evidence
artifact must retain its derivation: parent inputs and identities, the
operation or equation applied, implementation and tool versions, material
parameters, and the resulting artifact identity. A post-run verifier may also
inspect the output it is validating.

For avoidance of doubt, generated output **may** be used as a later contained
experiment's implementation input, configuration input, fixture, cache,
comparison source, or oracle input. Such reuse is not prohibited merely because
the material was generated by an earlier run. The mandatory conditions are
that the earlier run and its artifacts remain immutable, every derivative is
written into a new run, and the new evidence retains the complete derivation
chain described above.

The package lock, containment policy, baseline manifest, authored fixtures,
and copied baseline/candidate source are tracked control inputs even when a
tool creates them. Locally installed locked packages may reside in the
ignored `node_modules/`; dependencies are not experimental output.

The existing baseline and candidate are immutable historical comparison
surfaces. New stellar screen-palette implementation belongs in a new contained
surface rather than either historical tree. A refresh creates a new versioned
baseline rather than replacing an existing one.

The
[Stage 12 implementation topic](../../agents/topics/extraterrestrial/stage-12-implementation-topic.md#immutable-run-records)
owns the exact run number, slug, initialization, finalization, and
immutability rules.

Do not add or run an experimental `tests/` tree, unit-test suite or files,
test-framework dependency, or package test command during candidate work.
Prove concepts and cache strategies with focused runners under a declared
contained `runners/` directory. Cross-topic runners remain under `runners/`;
the active solar-zenith lane owns its runners under
`solar-zenith-cache/runners/`. A copied production test file is sealed
baseline/candidate source, not an experimental test owner; do not extend or
rely on it during this lane.

Provisional code is still subject to the ownership map in the active design.
Runners may orchestrate and measure the source, geometry, atmosphere, cache,
raster/visibility, and Color owners, but must not collect those
responsibilities into a runner or convenience object.

Every runnable must:

- derive the repository, source, and output roots from repository identity
  rather than `process.cwd()`;
- real-path-check all reads and writes and reject symlinks and junctions;
- keep relative, absolute, file-URL, and dynamic import closure inside this
  directory;
- declare and lock every bare package dependency;
- allocate every qualifying execution through the canonical run protocol; and
- inventory `src/algorithm32` and `src/flat32` directly before and after
  execution and require byte-for-byte equality. Do not invoke Git merely to
  build a protected-file inventory; Git state is not part of the scientific
  result.

Qualification runners may inspect production source read-only for contract
comparison. `src/algorithm32`, `src/flat32`, `scripts/algorithm32-star`, other
production/application code, and `C:\dev\poly-gc-react` remain read-only
comparison surfaces and never become runtime dependencies during this lane.
